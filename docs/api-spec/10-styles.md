# 10. Headless styling: functional CSS, the baseline stylesheet, no icons

The fourth amendment (§8.21–8.23). The package's stylesheets keep only what makes the viewer work.
The look moves to an opt-in `@ogdakke/fluidbox/baseline.css`, and the JavaScript draws no icons
(§2.21).

File and line references are to `packages/fluidbox/src` at `59cb944`. The stylesheets keep
their current names in the tables. `filmstrip.css` becomes `thumbnails.css` in step 1.7.

## 10.1 Unlayered functional CSS, layered baseline

```css
/* first line of baseline.css; the other stylesheets declare no layer */
@layer fluidbox-baseline;
```

- **The functional rules stay unlayered,** in `styles.css`, `thumbnails.css` and `sheet.css`,
  with today's selectors and specificity. Most are `:where(scope) [data-fluidbox-…]` (0,1,0), and
  some double an attribute to reach (0,2,0) (`styles.css:207`, `:231`). That beats element
  resets, which is the point. A site reset or Tailwind v3's unlayered preflight
  (`img, video { max-width: 100%; height: auto }`) is (0,0,1) and loses, as it does today. If
  these rules sat in a layer, any unlayered rule would beat them whatever its specificity, and
  sizing, fit and fill, positioning, the flight's transforms and the strip would break on most
  sites.
- **Only `baseline.css` is layered,** in `@layer fluidbox-baseline`, with every selector inside
  `:where()` (zero specificity). Any unlayered app rule beats it, and so does a rule in any app
  layer declared after it. An app with its own layers can put the baseline first in one line,
  `@layer fluidbox-baseline, base, components, utilities;`, but nothing depends on that: a layer
  declared first is weakest, and one declared later still loses to every unlayered rule.
- **The baseline never sets a property the functional CSS sets on the same element.** Unlayered
  beats layered, so such a baseline declaration would be dead. Where a surface needs a default
  and a themed value, the functional rule reads a token with a fallback, and the baseline sets
  only the token. The `Canvas` surfaces of §10.2 work this way. A build check enforces it (§9.4).
- **Overriding.** A look override is any plain app rule, since it competes only with the
  baseline. A mechanics override needs today's specificity, as now, or a mechanics custom
  property (§10.5).
- **`!important`.** The package's five `!important` declarations (`styles.css:173`, `:184`,
  `:260-261`; `sheet.css:50`, `:297`) hide the page thumbnail during a flight, keep the flight's
  source hidden, and stop pointer events after a dismiss. They stay unlayered, so they behave
  exactly as today. `baseline.css` has no `!important`: a layered `!important` beats an
  unlayered one, so it would beat the app's.
- **Reduced motion.** The package's reduced-motion rules are unlayered and beat a baseline
  transition on the same element. The baseline still puts every transition and animation inside
  `@media (prefers-reduced-motion: no-preference)` (risk R6 below), because some of its
  transitions are on elements the functional rules don't touch, and the docs give apps the same
  rule.

## 10.2 What "functional" covers

The rules without which layout, a gesture, a flight, the zoom or structural accessibility
breaks:

- the viewer covering the viewport, and its layering (`--layer-fluidbox`,
  `--layer-fluidbox-flight`);
- stage and slide layout, and contain and fill sizing (§5.4);
- the strip's scrolling and snapping, including hiding its scrollbar, which would otherwise
  change the measured slide size;
- the flight and transition layers;
- the zoom viewport and its transforms;
- the thumbnails' and sheet's mechanics;
- `[hidden]`, inert, opening and dismissing states, `touch-action` and `overscroll-behavior`;
- the visually hidden live region;
- reduced motion;
- forced-colours rules that keep content and focus visible;
- nothing that clips a focus ring (for example spin's `outline-offset: -2px`).

**Two keyframes look cosmetic but stay.** The runtime finds `fluidbox-gallery-controls-appear` and
`fluidbox-video-actions-reveal` by name and waits for them before it sets `open` and moves focus
(`dom-viewer-driver.ts:714-723`, `thumbnail-overlay-runtime.ts:368-371`). Their rules stay
functional. The baseline only sets the variable they end at
(`--fluidbox-gallery-control-opacity`, fallback 1).

**One deviation from the brief, recommended: keep a readable surface.** The brief moves the
backdrop's colour out. With only functional CSS the backdrop would be transparent, and so would
the sheet (risk R4): the page, or the photo, would show through the viewer's text. A see-through
dialog fails 1.4.3 contrast before any theming. So the functional CSS keeps system colours on
those two surfaces, as token fallbacks so the baseline and apps can theme them (§10.1):

```css
:where([data-fluidbox-viewer]) [data-fluidbox-backdrop] {
  background: var(--fluidbox-backdrop-background, Canvas);
}
:where([data-fluidbox-viewer]) [data-fluidbox-sheet] {
  background: var(--fluidbox-background, Canvas);
  color: var(--fluidbox-color, CanvasText);
}
```

`baseline.css` sets those three tokens on `[data-fluidbox-viewer]` and never the properties.

These are colour keywords, not a design. They follow light and dark mode and forced colours, and
any theme replaces them. Without them, "headless" would mean "broken until styled". The
overseer should confirm this with the user.

**What an unstyled viewer looks like.** It has a `Canvas` backdrop and the photo fitted on the
stage. Previous, Next and Close are plain text buttons in the viewer layer's normal flow, at its
top-left corner. They are operable and named, and they are hidden while opening and dismissing,
as today. That is the baseline for `bun run test` without `baseline.css`, which one smoke test
keeps (§9.4).

## 10.4 `baseline.css`

`@ogdakke/fluidbox/baseline.css` reproduces today's look exactly. It is imported by no entry. The
docs print it in full for anyone who would rather copy and own it.

```ts
import "@ogdakke/fluidbox/styles.css";
import "@ogdakke/fluidbox/thumbnails.css"; // when using thumbnails
import "@ogdakke/fluidbox/baseline.css"; // optional: today's look
```

- **Contents.** Every rule classified _look_ above: control positions and appearance, focus rings
  and their forced-colours and contrast variants, cursors, hover, the cosmetic fades, the
  placeholder colour, the error message's look, the busy spinner (on `[data-busy]`), the
  thumbnails' radius, opacity and selected bar, the sheet's radius, shadow and handle, the arrows'
  sheet anchoring, the embed Play button's look and the spin cursor. One file covers the core, the
  thumbnails and the sheet (§8.22). Rules for parts a page doesn't use match nothing.
- **Layer and specificity.** All of it is in `@layer fluidbox-baseline`, behind `:where()`. It
  sets no property the functional CSS sets on the same element (§10.1).
- **Tokens.** The look custom properties stay as the baseline's tokens (§10.5), so the common
  overrides are one variable: `--fluidbox-background`, `--fluidbox-color`,
  `--fluidbox-control-background`, `--fluidbox-focus-color`, `--fluidbox-backdrop-background`,
  `--fluidbox-backdrop-filter`, and so on.
- **Glyphs.** The baseline draws today's glyphs on controls that render their fallback label
  (`[data-fluidbox-default]`, §2.21). A `::before` gets `mask-image: var(--fluidbox-icon-close)`
  and `background-color: currentColor`, and the label text is visually hidden (clipped, not
  `display: none`, so it stays the accessible name). Controls holding the app's own content have
  no `data-fluidbox-default`, and the baseline leaves them alone. Each glyph is a token holding
  today's path as a `data:image/svg+xml` URL: `--fluidbox-icon-close`, `-previous`, `-next`,
  `-zoom-in`, `-zoom-out`, `-zoom-reset`, `-enter-fullscreen`, `-exit-fullscreen`, `-download`,
  `-share`, `-play-slideshow`, `-pause-slideshow`, `-retry` and `-embed-play`. Previous and Next
  mirror in RTL, as today (`styles.css:650-652`).
- **CSP.** A `data:` URL in `mask-image` is governed by `img-src`. `apps/examples/csp.html` runs
  under `default-src 'self'`, so it would block them. There, and on any strict page, either set
  the tokens to self-hosted files (`--fluidbox-icon-close: url("/icons/close.svg")`), or add
  `data-fluidbox-glyphs="off"` to an ancestor to show the text labels (§8.23). The CSP fixture does
  the first, so its test still sees glyphs and no violations.
- **Forced colours.** Under `@media (forced-colors: active)` the baseline drops the mask and shows
  the text, because a forced `background-color` would hide a masked glyph.
- **Today's look, exactly.** The migration rule is that the fixtures, examples and docs import
  `baseline.css`, and the visual snapshots (`collapsed-visual`, `interactions`, `motion`) don't
  move. The one expected difference is antialiasing: a masked glyph and an inline stroked SVG of
  the same path can differ by a pixel at their edges. If a snapshot moves, the diff is reviewed and
  must touch glyph edges only. Anything else is a bug in the split.

## 10.6 Data attributes: the styling contract

Everything a theme selects on is a data attribute, listed in §1.11 and on the CSS reference page.
They are the styling contract: renaming one is a breaking change, so they are covered by
`tests/public-api.contract.ts` through the `css-api.ts` list. This amendment adds:

| Attribute                                              | On                          | Meaning                                              |
| ------------------------------------------------------ | --------------------------- | ---------------------------------------------------- |
| `data-fluidbox-default`                                | a control                   | It renders its fallback label text, not app content. |
| `data-busy`                                            | a slide                     | Its media is loading (with `aria-busy`).             |
| `data-error`                                           | a slide                     | It is in its error state.                            |
| `data-fluidbox-retry`                                  | the Retry control           |                                                      |
| `data-fluidbox-loading`, `data-fluidbox-error-content` | `Loading` and `Error` parts |                                                      |
| `data-fluidbox-glyphs="off"`                           | any ancestor (app-set)      | The baseline shows text instead of glyphs.           |
| `data-fluidbox-label="content"`                        | a control (app-set, markup) | Name it by its content.                              |

`data-fluidbox-icon`, on the SVGs the package drew, is removed. It is reused only as the attribute
of `<template data-fluidbox-icon="close">` in markup (§2.21).

## 10.7 What the consumer owns: an accessibility checklist

Printed on the styling page, and checked against `baseline.css`:

1. A visible focus style on every control, thumbnail, hotspot and the sheet, with 3:1 contrast
   against what is behind it (WCAG 2.4.7, 2.4.11/2.4.13 at AAA).
2. Text and icon contrast of 4.5:1 for text and 3:1 for icons, over the backdrop _and_ over the
   photo where controls overlap it (1.4.3, 1.4.11).
3. Controls at least 24 × 24 CSS pixels, or spaced to that (2.5.8).
4. The current thumbnail marked by more than opacity or colour alone (1.4.1).
5. No `display: none` on a control's label text if the control has no other name. Hide it
   visually instead.
6. Every transition inside `prefers-reduced-motion: no-preference`.
7. Icons inside controls marked `aria-hidden="true"`. The control's label names it.
8. Check forced colours. The functional CSS keeps content and focus visible there, and a theme
   should not use `forced-color-adjust: none` on controls.
